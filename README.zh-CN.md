Pi-function 把你已安装的 Pi 插件组织成**应用场景**：做网页、写文章、做游戏、做报告、做数据图表……单独输入 `/function` 时，先选**怎么执行**（工作流），再选**做什么**（应用场景）。`/function resume` 和带需求文本的 `/function` 共用项目进度分析和装配确认。带需求时，再结合原文判断这轮需要什么。

场景和工作流的 ID 对每个用户都固定；具体由哪些插件、技能来填充，则**从当前电脑自动识别**，保存在每用户的能力画像里。源码不假设你装了哪套插件。

单文件、常驻、无依赖、无网络请求、无遥测。

## 为什么做这个

装上十几个插件、几十个 Skill 之后，真正的问题不是“缺工具”，而是**乱**：

- 想要的工具没开，用不上的工具全占着上下文，还干扰判断；
- 同一个能力被三四个插件重复实现，不知道该用哪个；
- 每次换任务都要手动想起“这次该开哪些”，漏掉一个就得重来；
- 装得越多，模型越容易被无关工具带偏，回答里混进根本不存在的工具。

Pi-function 就是治这个的。目标是**用最方便、最准确、最快速、最高效的方式，合理利用本机所有已安装的 Skill、插件和工具**：

| 目标 | 怎么做到 |
|---|---|
| **最方便** | 一句 `/function` 或一句人话。不用记插件名、不用查有哪些工具，菜单里每个选项都写着“什么时候该选它” |
| **最准确** | 需求理解交给模型（它读得懂整段语义），工具怎么开交给本地确定性算法（不会自由发挥）；场景契约要求的能力**强制补全**，宁可多开也不漏 |
| **最快速** | 本地决策是毫秒级的：`analyzeNeed` 0.8ms，装配一次改完工具集立即生效；不需要联网、不调用模型也能完成菜单/固定场景/工作流 |
| **最高效** | 装配后只保留这次真正要用的工具（内置 + 本次插件），其余可选工具全部关掉；系统提示里列清“这次开了什么、有哪些技能和命令”，模型不会拿不存在的工具硬做 |

底线只有一条：**最不能接受的场面是用户没用到需要的工具。** 所以有自动补全、有漏用检查、有缺装告警，也有 `/function status` 告诉你“为什么某个工具没出现”。

## 安装

```bash
pi install npm:pi-function
```

也可以固定版本或用 git：

```bash
pi install npm:pi-function@3.0.0
pi install git:github.com/ppTeyven/pi-function@v3.0.0
```

本地开发：

```bash
pi install ./path/to/pi-function
```

也可以把 `function-menu.js` 放进 `~/.pi/agent/extensions/`。Pi 启动时自动加载。

如果安装时 Pi 会话已经开着，需要 `/reload` 或重启。否则 `/function ...` 会被当作普通提示发给模型，扩展无法拦截。

需要 Node 20+，以及支持 `pi.registerCommand`、`pi.setActiveTools`、`pi.getCommands()` 返回技能的 Pi 版本。

## 使用说明

### 第一次使用

1. 安装扩展后执行 `/reload`（或重启 Pi），确认 `/function` 能被识别。
2. 输入 `/function`，先弹出子功能菜单；选择“场景装配”后进入工作流和场景选择器。
3. **先选工作流**：决定这次怎么执行，例如“结构先行”“原型先行”“评审守门”。工作流会带上自己的执行套餐，场景再补充领域能力。
4. **再选应用场景**：决定最终要做出什么，例如网页、文章、游戏、报告。
5. 阅读装配提案，确认后才会切换工具。点 **No** 不会改动任何东西。
6. 装配完成后直接描述任务即可；扩展不会自动执行你的需求。

如果你已经明确只想用某套流程，输入 `/function workflow`，只选工作流并启用该套餐，不绑定应用场景。

### 命令一览

| 命令 | 行为 |
|---|---|
| `/function` | 先选子功能（场景装配 / 项目续接 / 仅工作流 / 画像 / 扫描 / 状态 / 统计 / 还原 / 手动归类）；选“场景装配”后选择工作流 → 应用场景 → 确认 |
| `/function resume` | 读取 HANDOFF / ROADMAP / 决策文档、Git 状态与最近会话，报告整个项目的阶段、未完成项、阻塞、下一步和建议组合；确认前不改任何工具 |
| `/function workflow` | 只选工作流并启用，不绑定任务场景 |
| `/function <需求>` | 先做与 `resume` 相同的项目进度分析，再结合需求提出方案；确认后才装配，不执行任务本身 |
| `/function profile` | 查看生成的能力画像：角色、评分、未归类条目和画像路径 |
| `/function scan` | 重新扫描已安装插件、本地扩展和技能，并重建能力画像 |
| `/function status` | 查看当前工作流 × 场景（或仅工作流模式）、已启用的插件工具 |
| `/function assign <名称> <场景id\|none>` | 手动覆盖某个插件/技能的绑定 |
| `/function stats`、`/function stats reset` | 查看统计；显式 `reset` 才清空计数（也支持 `clear`） |
| `/function off` | 恢复全局默认工具（考虑 Pi 的 `defaultTools`），不是回滚到之前的快照 |

`/function resume` 是项目续接报告；简历 / 求职场景的固定 id 也叫 `resume`，用 `/function scenario resume` 或“场景装配”选择器进入。

`/pi-function` 是别名。

工作流选择器说明执行过程，并显示该工作流套餐的插件/技能数；场景选择器显示领域插件和技能数。典型流程：

```text
/function

第 1 步：先选工作流（怎么执行）
  outline · 结构先行 — ★ 推荐 · 先出提纲或方案，确认后再展开
  direct · 直接产出 — 需求清楚、范围小；直接做，不先写计划
  ...

第 2 步：再选应用场景（做什么）
  webpage · 网页 / 落地页 / 官网 — 2 个插件 · 3 技能（frontend-design、...）
  ...

## 装配：结构先行 × 网页 / 落地页 / 官网
**工作流**：先给出结构/目录/页面清单，确认后再产出
**场景**：官网、落地页、营销页、响应式页面

**将启用的插件与功能**
- ... — 能力描述、工具、命令、技能
...
```

### 三种入口怎么选

| 你的情况 | 推荐输入 | 会发生什么 |
|---|---|---|
| 还没想好做什么，想先看看有哪些组合 | `/function` | 工作流 → 应用场景 → 确认装配 |
| 只想固定执行方式，不限定产物 | `/function workflow` | 只选工作流，启用其套餐，不绑定任务场景 |
| 已经有一句话需求 | `/function "做一个产品官网，并写一篇发布文章"` | 项目进度 + 需求 → 选工作流 → 看提案 → 确认后装配 |
| 接手一个已有项目 | `/function resume` | 扫描项目证据 → 给出进度、阻塞、下一步 → 推荐全项目组合；确认后才装配 |

### 选择器与确认

选择器每一行大致是：

```text
webpage · 网页 / 落地页 / 官网 — 2 个插件 · 3 技能（frontend-design、...）
```

- 前面的 `webpage` 是固定场景 ID，跨用户、跨机器都不变。
- “插件/技能”来自当前电脑的能力画像，不同用户可能不同。
- 装配提案会列出将启用的插件、工具、技能和仍需手动执行的命令。
- 项目续接和自由文本都先出项目报告，再走同样的工作流选择、提案和确认。选择工作流不等于同意装配；确认框点 **No** 不切换工具。

### 日常维护

| 场景 | 操作 |
|---|---|
| 想看当前装配了什么 | `/function status` |
| 想确认插件/技能归类是否合理 | `/function profile` |
| 想恢复全局默认工具 | `/function off` |
| 新装了插件或技能 | `/function scan` |
| 某个插件/技能分错了场景 | `/function assign <包名或 skill:名> <场景id>`；`none` 表示不自动归入 |
| 想重新看完整目录 | 再输入一次 `/function` |

### 常见问题

**输入 `/function` 没有反应，反而被当成普通消息？**

扩展还没被当前会话加载。执行 `/reload`，或重启 Pi。

**选择器里没有我刚装的插件/技能？**

先 `/function scan`。仍没有时，确认该包确实注册了工具/命令，或技能有 `SKILL.md`；然后用 `/function assign` 手动指定。

**装配后觉得工具不够？**

先 `/function status` 看当前组合，再换一个工作流/场景，或用 `/function assign` 调整能力画像绑定。

**`/function "需求"` 会自己开始干活吗？**

不会自动开始项目工作。模型只结合项目进度和原文提方案，你确认后才启用工具。若要开始执行任务，再发指令。

**多个项目/会话会互相影响吗？**

工具切换作用于当前会话。恢复时先看当前分支；分支已关闭的组合不会被用户级后备记录复活。能力目录、手动归类和统计仍是用户级共享文件，并非项目权限隔离。

## 工作流

工作流 = **过程 + 执行套餐**。每个工作流绑定一组通用能力角色（不是写死的包名），由当前用户的画像解析成实际插件和技能；应用场景再补充领域能力。套餐可以重叠：例如排查和评审都需要代码理解与验证能力，这是正常的。

| id | 工作流 | 过程 | 套餐角色（按画像解析） | 适用 |
|---|---|---|---|---|
| `direct` | 直接产出 | 读目标 → 直接做 → 自检 | 仅核心工具 | 需求清楚、范围小；不先写计划 |
| `outline` | 结构 / 原型先行 | 提炼目标 → 出结构/方案或最小原型 → 确认 → 展开 | 计划评审、任务跟踪、记忆 | 先要提纲、目录、实施步骤，或先看最小原型方向 |
| `research` | 证据先行 | 列问题 → 多源取证 → 交叉核对 → 带出处结论 | 联网、仓库知识、记忆、文档 | 事实不确定、需要对比或可追溯 |
| `debug` | 排查修复 | 复现 → 定位根因 → 最小修复 → 回归 | 代码理解、验证、上下文、简化 | 有明确故障、报错或行为异常 |
| `parallel` | 并行探索 | 拆工作包 → 多路推进 → 汇总去重 → 验收 | 子代理、编排、任务跟踪 | 任务可拆成互不依赖的几块，或多方案对比 |
| `review-gate` | 评审 / 迭代守门 | 初稿 → 独立审查或收集反馈 → 只改关键差距 → 复验交付 | 子代理、编排、代码理解、验证、简化、计划评审 | 高风险改动、发布前检查、重要文档，或需要按反馈多轮打磨 |
| `phased` | 阶段推进 | 规格 → 计划 → 逐阶段执行 → 阶段验收 | 阶段引擎、计划评审、任务跟踪、上下文 | 多阶段长任务、复杂迁移、持续开发 |
| `offline` | 隐私 / 离线 | 盘点本地资源 → 不联网 → 完成本地部分 → 列出联网缺口 | 本地记忆（不启用联网能力） | 敏感内容、不能外发、最小联网面 |

> 表中是能力角色，不是具体插件名。你的画像会把角色解析成你电脑上实际安装的插件和技能；不同用户可以是不同的包，工作流 ID 和语义不变。

## 能力画像

首次加载和每次扫描时，Pi-function 会读取：

- 已安装的 npm 插件；
- 本地扩展；
- 已注册的工具、命令；
- 技能名称与描述。

然后按通用能力角色（代码理解、网页、写作、设计、子代理、任务跟踪、浏览器、视觉、记忆、文档、发布、测试等）打分，写入：

```text
~/.pi/agent/function-menu.profile.json
```

画像包含“角色 → 插件/技能”的绑定、描述和指纹。新装插件或技能会改变指纹，触发自动重建。这个文件属于当前用户，不应提交到仓库。

场景目录和工作流套餐都在运行时从画像填充，所以同一个 `webpage`、`article` ID 在不同电脑上可以使用完全不同的工具，而扩展源码不变。

手动覆盖保存在 `~/.pi/agent/function-menu.json`，重建画像时不会丢失。

### 整理规则

Pi-function 不维护写死的插件清单，而是用多路信号给每个包/技能打分：

- 包名或技能名：**5 分**；
- 已注册的工具名或命令名：**3 分**；
- 包内贡献的技能名：**2 分**；
- 描述关键词：**1 分**。

角色默认至少要达到 **2 分**才会被采纳；角色级 `deny` 规则会过滤已知误匹配，例如搜索技能不能变成测试工具、公文排版技能不能变成设计工具。名称强匹配优先于描述级 deny。每个条目最多进入 **3 个包角色**或 **2 个技能角色**，避免一个包污染多个场景。需要环境变量的包（例如云浏览器 key）在变量缺失时跳过，但本地技能仍然保留。

运行 `/function profile` 可以查看结果：每个角色命中的插件/技能及分数、未归类清单、画像文件路径。需要人工修正时仍可用 `/function assign`。

## 项目续接

`/function resume` 回答的是“这个项目整体下一步该做什么”，而不是“这句话需要什么”。适合隔了一段时间回来、接手别人的 HANDOFF，或上下文被压缩/重置之后。

它会读取（有上限，避免把大仓库拖慢）：

- `HANDOFF.md`、`DECISIONS.md` / ADR、`ROADMAP.md`、`.planning/`、README 等项目文档；
- Git 分支、短 HEAD、未提交文件、最近提交；
- 当前会话里最近的消息、助手回复和压缩摘要。

报告把证据和推断分开：

- 阶段判断（有阻塞 / 进行中 / 交接 / 信息不足）；
- 已完成、未完成、阻塞/风险、下一步；
- 可能的应用场景和建议工作流；
- 该组合会启用的插件与技能。

`/function resume` 从当前 Pi **会话工作目录**定位项目，而不是从 pi-web 的安装目录开始。README 命令表、围栏代码示例和明确的“暂无阻塞”不是阻塞证据；用 `## 阻塞` 下的列表或 `阻塞：原因` 记录实际问题。

无交互 UI 时只输出报告；取消流程不切换工具，也不保存本次扫描到目录/画像文件。确认后才装配，不执行项目工作。报告可展示文档摘录，系统提示中的项目段只带阶段和数量。同一项目恢复已确认的项目选择，不自动转到另一个项目读取旧文档。

## 动态需求

`/function "做一个产品官网，并写一篇发布文章"` 和 `resume` 的区别只在分析输入：一个看项目进度加本轮需求，另一个只看项目进度。

1. 读取同一套项目文档、Git 和最近会话，先展示进度报告，同时列出本轮需求的本地候选；需求原文不写入这份预览。
2. 选择工作流，或点“让模型决定”；在这一步按 Esc，保留原文且不发送给模型。
3. 模型结合项目证据与原文，用 `suggest_scenario` 查候选、通过 `assemble_scenario` 提方案。场景、工作流各最多三个；用户已选的工作流不被覆盖。
4. 与 `resume` 一样，展示提案、确认并核对能力缺口后才装配。取消不切换工具，需求原文会放回编辑框。

无交互 UI 时，两者只报告，不主动发起模型分析或装配。模型装配工具被停用时，仍可按本地候选预览并确认，不会为分析先切换工具。使用云端模型时，进入模型分析后，模型可看到发送给它的需求和项目报告；只想在本地看项目报告时用 `/function resume`。

## 装配会改变什么

- 启用所选插件的工具；
- 保留核心工具（`read`、`bash`、`edit`、`write`、`grep`、`find`、`ls`）；
- 停用其他插件的可选工具；
- 把工作流和应用场景的流程注入系统提示；
- 不卸载插件代码；技能与命令仍由 Pi 管理。装配不是沙箱或权限控制。

## 开发

```bash
npm test
```


测试用临时 Pi 目录，不读取开发者的已装扩展。除命令、取消、恢复、分类与覆盖外，也通过公共装配入口逐一检查每个固定场景 × 工作流。

临时验收脚本（SDK 冒烟、并发写竞态等）只在需要时编写、运行，不存入仓库；可长期重跑的只有上面的 `npm test`。
